# Finish line and scaling model

## What finished means

The project is ready to stop its architecture conversion when all of the
following are true for a declared support set:

1. No known confidently wrong structural claim remains in the release corpus.
2. Common mechanisms are owner-bound, source-grounded, and projected from one
   canonical fact.
3. Missing source, unsupported syntax, and new mechanisms remain opaque or
   partial rather than inheriting a conventional architecture.
4. HTML, drills, cards, JSON, parameters, and conformance do not independently
   reinterpret structure.
5. Semantic config tables, identity branches, conventional defaults, and
   superseded compatibility paths are deleted for covered mechanisms.
6. Preservation, counterexample, and receipt checks pass on an unchanged tree.

Completion is not defined as understanding every repository on the Hub. The
coverage denominator must be measurable: official architecture classes in
explicitly supported Transformers and Diffusers versions, plus a published
representative corpus.

## How new models scale after that

### New checkpoint, supported class

No code change. Config supplies checkpoint-specific dimensions, counts, and
selected values; the existing mechanism facts and projections apply.

### New class, known mechanisms and known source shapes

No code change. The owner-bound program index normalizes the construction and
call graph into existing mechanisms.

### New source syntax for a known mechanism

One shared source-index or binding improvement, with equivalent controls. The
fix is not named after the reported model and benefits every class using the
syntax.

### Genuinely new mechanism

One mechanism interpreter, canonical fact/region contract, reusable projection,
and representative tests. This is legitimate product expansion and cannot be
eliminated by infrastructure.

### Unresolvable or out-of-scope implementation

An honest unresolved component with the established geometry and declarations
that are actually known. It does not block release of supported mechanisms and
does not receive a guessed substitute.

## Scope control

The project must not chase every inspected config field as new architecture.
Each field is classified as one of:

- a checkpoint value bound to a proven mechanism;
- an address or component declaration;
- display-only metadata;
- non-architectural with an exact owner and reason;
- unresolved mechanism input;
- unsupported/out of scope.

Only the first and fifth categories can require new mechanism work.

## Growth control

Each mechanism change reports:

- production lines added and deleted;
- old authority paths removed;
- temporary bridges added or retired;
- debt occurrences classified or eliminated;
- positive, negative, equivalent, and missing-source witnesses.

Sustained production growth without deletion is a stop signal. The intended
long-run shape is a small shared acquisition/evidence/projection core plus
mechanism interpreters, not permanent scaffolding around old parsers.
